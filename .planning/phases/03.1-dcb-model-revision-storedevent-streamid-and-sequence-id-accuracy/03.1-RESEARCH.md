## Summary

Phase 03.1 is a breaking revision of the core type layer to align with the Dynamic Consistency Boundary (DCB) pattern. The fundamental change is replacing per-stream identity and sequencing with a flat, globally-ordered log where events carry opaque string tags. Concurrency control shifts from "what version is this stream at?" to "have any events matching this query appeared after position N?". This is a more powerful and general model that enables multi-entity consistency boundaries from a single event.

The implementation touches six files in `event-sourcing` core and one file in `event-sourcing-logstore-inmemory`. Existing test coverage (16 unit tests + 9 integration tests + 17 inmemory unit tests = 42 total) must be completely replaced with tag-based equivalents. All removed types (`StreamId`, `StreamSequenceId`, `InvalidStreamId`, `AppendCondition` enum) are breaking API changes — no backward compatibility needed since Phase 4 depends on these types and will be revised before implementation.

The most complex design choices are (1) the `Query` type representation and (2) the `AppendCondition` check semantics. The DCB reference implementation (bwaidelich/dcb-eventstore) establishes both patterns; this research draws on training knowledge of that PHP implementation and the general DCB specification.

**Primary recommendation:** Use a simple struct-based `Query` with a `Vec<Criterion>` where each criterion is an enum variant (TagMatch, EventTypeMatch), composed with AND semantics between criteria and OR within each variant. This matches the DCB spec's intent and is ergonomic in Rust.

## Architecture Patterns

### Recommended Module Layout

The current module layout (`types.rs`, `event.rs`, `error.rs`, `store.rs`, `event_log.rs`) can absorb the new types without adding new modules. However, `Query` and `Tag` are substantive enough to benefit from their own module:

```
event-sourcing/src/
├── lib.rs              # Re-exports (updated)
├── types.rs            # GlobalSequenceId, NewEvent, Tag (add Tag here; remove StreamId, StreamSequenceId)
├── query.rs            # Query type (NEW MODULE — Query is a first-class concept)
├── event.rs            # StoredEvent (remove stream_id, stream_sequence; add tags)
├── error.rs            # AppendCondition (struct, not enum), AppendError, StoreError
├── store.rs            # LogStore trait (revised signatures)
├── event_log.rs        # EventLog<S>, EventLogError, EventStreamExt
└── tests/
    event_log_integration.rs  # Rewritten for tag-based model
```

Placing `Tag` in `types.rs` keeps all primitive types co-located. `Query` warrants its own module because it will grow with Phase 4 (projections query the same log), and separating it avoids making `types.rs` unwieldy.

### Pattern 1: Tag Newtype

**What:** Non-empty string wrapper with validation on construction. Derives `Hash + Eq` to work in `HashSet`.

**When to use:** Every event carries a `HashSet<Tag>`, every query filters on `HashSet<Tag>`.

```rust
// Source: training knowledge of Rust newtype pattern [ASSUMED]
#[derive(Debug, Clone, PartialEq, Eq, Hash, serde::Serialize, serde::Deserialize)]
pub struct Tag(String);

#[derive(Debug, Clone, PartialEq, Eq, thiserror::Error)]
#[error("tag must not be empty")]
pub struct InvalidTag;

impl Tag {
    pub fn new(value: impl Into<String>) -> Result<Self, InvalidTag> {
        let value = value.into();
        if value.is_empty() {
            return Err(InvalidTag);
        }
        Ok(Tag(value))
    }

    pub fn as_str(&self) -> &str {
        &self.0
    }
}

impl std::fmt::Display for Tag {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        write!(f, "{}", self.0)
    }
}
```

**Design note:** Deriving `serde::Serialize/Deserialize` directly on the newtype is preferable to a custom impl — the SQLite store (Phase 8) will store tags as JSON. Adding serde at the type level now avoids retrofitting.

**On character validation:** The DCB spec treats tags as opaque — "non-empty" is the only constraint that makes semantic sense. Length limits are artificial. Recommendation: non-empty only, no length cap, no character restrictions. [ASSUMED]

### Pattern 2: Query Type Design

The DCB spec defines a `Query` as a set of `Criteria`, where each criterion specifies which event types and/or tags it matches. An event matches the query if it matches **any** criterion (OR across criteria). Within a single criterion, it matches if it carries **all** required tags AND is one of the required event types (AND within criterion). This models the "AND within a dimension, OR across criteria" shape. [ASSUMED — based on training knowledge of bwaidelich/dcb-eventstore]

```rust
// Source: training knowledge of DCB specification [ASSUMED]
/// A single filter criterion. An event matches if ALL of the following hold:
/// - event_types is empty OR event.event_type is in event_types
/// - tags is empty OR event.tags is a superset of tags (all required tags present)
#[derive(Debug, Clone)]
pub struct Criterion {
    pub event_types: Vec<String>,   // empty = match all event types
    pub tags: HashSet<Tag>,         // empty = match any tags
}

/// A query is a set of criteria. An event matches the query if it matches ANY criterion.
/// An empty criteria vec means "match nothing" — use Query::all() for match-all behavior.
#[derive(Debug, Clone)]
pub struct Query {
    pub criteria: Vec<Criterion>,
}

impl Query {
    /// Match all events — use in place of the removed read_all().
    pub fn all() -> Self {
        Query {
            criteria: vec![Criterion {
                event_types: vec![],
                tags: HashSet::new(),
            }],
        }
    }

    /// Match events carrying ALL of the specified tags.
    pub fn match_tags(tags: impl IntoIterator<Item = Tag>) -> Self {
        Query {
            criteria: vec![Criterion {
                event_types: vec![],
                tags: tags.into_iter().collect(),
            }],
        }
    }

    /// Match events of any of the specified event types.
    pub fn match_event_types(event_types: impl IntoIterator<Item = String>) -> Self {
        Query {
            criteria: vec![Criterion {
                event_types: event_types.into_iter().collect(),
                tags: HashSet::new(),
            }],
        }
    }

    /// Combine additional criteria (OR across the query).
    pub fn or(mut self, criterion: Criterion) -> Self {
        self.criteria.push(criterion);
        self
    }
}
```

**Matching logic:**
```rust
// Source: training knowledge of DCB specification [ASSUMED]
fn event_matches_criterion(event: &StoredEvent, criterion: &Criterion) -> bool {
    let type_match = criterion.event_types.is_empty()
        || criterion.event_types.contains(&event.event_type);
    let tag_match = criterion.tags.is_empty()
        || criterion.tags.iter().all(|t| event.tags.contains(t));
    type_match && tag_match
}

fn event_matches_query(event: &StoredEvent, query: &Query) -> bool {
    if query.criteria.is_empty() {
        return false; // empty query = match nothing
    }
    query.criteria.iter().any(|c| event_matches_criterion(event, c))
}
```

**Note on `Query::all()` edge case:** When `AppendCondition` uses `Query::all()`, every append would conflict with any prior event after `after`. This is intentional — it expresses "I need to be the only writer since position N." Unusual but valid. [ASSUMED]

### Pattern 3: Revised AppendCondition and Conflict Check

```rust
// Source: training knowledge of DCB specification [ASSUMED]
pub struct AppendCondition {
    pub query: Query,
    pub after: GlobalSequenceId,
}
```

**Conflict check semantics:** When `condition: Some(AppendCondition { query, after })`, the store must:
1. Scan events with `global_sequence > after`
2. For each event, check `event_matches_query(event, &query)`
3. If ANY such event is found → return `AppendError::ConcurrencyConflict`
4. If NONE found → proceed with append

This scan happens **under the write lock** in `InMemoryLogStore` (same lock as the append itself). This is the DCB "optimistic" check — it checks that the caller's view of the world (up to position `after`) is still current relative to its query scope.

**Key insight:** The `after` field is typically set to the `GlobalSequenceId` returned by the most recent `query()` call the caller made before deciding to append. The condition fails if any relevant event arrived between that read and this write.

### Pattern 4: LogStore::query Signature

The existing `LogStore` uses native `async fn in trait` (Rust 1.75+, stable) with static dispatch only (`S: LogStore`). This pattern continues unchanged.

```rust
// Source: existing store.rs [VERIFIED]
pub trait LogStore: Send + Sync {
    type EventStream: futures_core::Stream<Item = Result<StoredEvent, StoreError>> + Send;

    fn append(
        &self,
        events: Vec<NewEvent>,
        condition: Option<AppendCondition>,
    ) -> impl std::future::Future<Output = Result<GlobalSequenceId, AppendError>> + Send;

    fn query(
        &self,
        query: Query,
        from: GlobalSequenceId,
    ) -> impl std::future::Future<Output = Result<Self::EventStream, StoreError>> + Send;

    fn current_sequence(
        &self,
    ) -> impl std::future::Future<Output = Result<GlobalSequenceId, StoreError>> + Send;
}
```

The return type `Result<Self::EventStream, StoreError>` (not `Self::EventStream` directly) preserves the existing convention: outer `Result` for "couldn't start reading" (e.g., connection failure), stream items of `Result<StoredEvent, StoreError>` for mid-stream errors. This matches existing design decision D-13 from Phase 1 context.

### Pattern 5: EventStreamExt Blanket Impl

```rust
// Source: training knowledge of futures::StreamExt pattern [ASSUMED] + design in CONTEXT.md D-28
use futures_core::Stream;

#[derive(Debug, thiserror::Error)]
pub enum StreamError {
    #[error("stream was empty, expected exactly one event")]
    Empty,
    #[error("stream had multiple events, expected exactly one")]
    Multiple,
    #[error("stream error: {0}")]
    Store(#[source] StoreError),
}

pub trait EventStreamExt: Stream<Item = Result<StoredEvent, StoreError>> {
    async fn single(self) -> Result<StoredEvent, StreamError>
    where
        Self: Sized + Unpin;

    async fn first(self) -> Result<Option<StoredEvent>, StoreError>
    where
        Self: Sized + Unpin;
}

impl<S: Stream<Item = Result<StoredEvent, StoreError>> + Sized + Unpin> EventStreamExt for S {
    async fn single(mut self) -> Result<StoredEvent, StreamError> {
        use futures::StreamExt; // for .next()
        let first = self.next().await;
        match first {
            None => Err(StreamError::Empty),
            Some(Err(e)) => Err(StreamError::Store(e)),
            Some(Ok(event)) => {
                match self.next().await {
                    None => Ok(event),
                    Some(_) => Err(StreamError::Multiple),
                }
            }
        }
    }

    async fn first(mut self) -> Result<Option<StoredEvent>, StoreError> {
        use futures::StreamExt;
        match self.next().await {
            None => Ok(None),
            Some(Err(e)) => Err(e),
            Some(Ok(event)) => Ok(Some(event)),
        }
    }
}
```

**Implementation notes:**
- `EventStreamExt` lives in `event_log.rs` alongside `EventLog` (or in a new `stream_ext.rs`). It should be re-exported from `lib.rs`.
- `StreamError` is a distinct error type from `StoreError` — `single()` has richer failure modes (Empty, Multiple) that don't belong on `StoreError`. This is the recommended approach over folding into `StoreError`. [Claude's Discretion exercised]
- The `futures` crate's `StreamExt` provides `.next()`. Since `futures` is already a workspace dependency, no new deps needed.
- `Unpin` bound is required for `StreamExt::next()` on the trait method receiver. The `InMemoryEventStream` (`stream::Iter`) is `Unpin`, so this is not a practical constraint.

### Pattern 6: ConcurrencyConflict Metadata

**Recommended:** Carry the conflicting event's position and the query that was checked.

```rust
// Source: Claude's discretion [ASSUMED]
#[derive(Debug, thiserror::Error)]
pub enum AppendError {
    #[error("concurrency conflict: event at position {conflicting_position} matched query after position {checked_after}")]
    ConcurrencyConflict {
        /// Position of the first conflicting event found.
        conflicting_position: GlobalSequenceId,
        /// The `after` position from the AppendCondition — what the caller considered current.
        checked_after: GlobalSequenceId,
    },

    #[error("storage failure: {0}")]
    StorageFailure(#[source] Box<dyn std::error::Error + Send + Sync>),
}
```

**Rationale:** The caller who gets `ConcurrencyConflict` needs to know:
1. Where to re-read from (`checked_after + 1`) — i.e., what they missed
2. Where the conflict was found (`conflicting_position`) — useful for debugging and logging

Including the `Query` in the error would be useful but adds complexity (Query must be `Clone` and Debug, which it already is). However, including the query in the error is redundant since the caller already has it. Keep it simple: `conflicting_position` + `checked_after`.

`EventLogError::ConcurrencyConflict` mirrors this shape identically, following the existing layer separation pattern.

### Pattern 7: InMemoryLogStore Internal Data Structure

The current `HashMap<StreamId, Vec<StoredEvent>>` must change. Since there are no more streams, the store becomes a flat ordered list of events:

**Query filtering in InMemoryLogStore:**
```rust
// Source: derived from matching logic above [ASSUMED]
async fn query(
    &self,
    query: Query,
    from: GlobalSequenceId,
) -> Result<Self::EventStream, StoreError> {
    let state = self.inner.read().await;
    let events: Vec<Result<StoredEvent, StoreError>> = state
        .events
        .iter()
        .filter(|e| e.global_sequence >= from && event_matches_query(e, &query))
        .cloned()
        .map(Ok)
        .collect();
    drop(state);
    Ok(stream::iter(events))
}
```

**Append with AppendCondition check:**
```rust
// Source: derived from DCB semantics [ASSUMED]
async fn append(
    &self,
    events: Vec<NewEvent>,
    condition: Option<AppendCondition>,
) -> Result<GlobalSequenceId, AppendError> {
    if events.is_empty() {
        let state = self.inner.read().await;
        return Ok(state.current_sequence());
    }

    let mut state = self.inner.write().await;

    // Check condition BEFORE allocating sequence IDs (under write lock = atomic).
    if let Some(AppendCondition { query, after }) = condition {
        if let Some(conflict) = state
            .events
            .iter()
            .find(|e| e.global_sequence > after && event_matches_query(e, &query))
        {
            return Err(AppendError::ConcurrencyConflict {
                conflicting_position: conflict.global_sequence,
                checked_after: after,
            });
        }
    }

    // Allocate global sequence IDs and build stored events under write lock.
    let mut last_global_seq = GlobalSequenceId::ZERO;
    for new_event in events {
        let global_seq = GlobalSequenceId::new(state.next_global_seq);
        state.next_global_seq += 1;
        let stored = StoredEvent {
            global_sequence: global_seq,
            event_type: new_event.event_type,
            payload: new_event.payload,
            tags: new_event.tags,
            timestamp: SystemTime::now(),
        };
        state.events.push(stored);
        last_global_seq = global_seq;
    }

    Ok(last_global_seq)
}
```

### Anti-Patterns to Avoid

- **Do NOT use `Vec<Tag>` on StoredEvent or Query.** Duplicate tags on an event are meaningless; `HashSet` enforces uniqueness and makes containment checks O(1). [VERIFIED: D-06 from CONTEXT.md]
- **Do NOT use `.contains()` on `Vec<String>` for event_type filtering.** Use `HashSet<String>` internally in `Criterion.event_types` for O(1) lookup when filtering large event sets. [ASSUMED — performance consideration]
- **Do NOT hold the RwLock across `.await` points.** The existing InMemoryLogStore code already respects this (explicit `drop(state)` before returning). Maintain this pattern. [VERIFIED: existing code]
- **Do NOT expose `stream_id` in any public API.** All references to `StreamId` in `event_log_integration.rs` and inmemory tests must be completely replaced, not just adapted. [VERIFIED: D-09 from CONTEXT.md]
- **Do NOT add `Query::none()` or empty-criteria behavior to match everything.** Empty criteria means "match nothing" — `Query::all()` is the explicit empty-filter escape hatch. [ASSUMED — matches DCB spec intent]

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Async stream over a Vec | Custom iterator struct | `futures::stream::iter()` | Already in dep graph; zero-cost; preserves EventStream type contract |
| Stream consumption utilities | Custom `.next()` calls in user code | `EventStreamExt::single()` / `::first()` | The entire point of D-28 |
| Tag serialization | Custom serde impl | `#[derive(Serialize, Deserialize)]` on `Tag(String)` | Serde newtype pattern handles this transparently |
| Lock-free global counter | `AtomicU64` separate from lock | Allocate under existing write lock | Allocation and conflict check must be atomic together — separate atomic would create a TOCTOU race |

## Common Pitfalls

### Pitfall 1: Empty Events Vec in append()

**What goes wrong:** Caller appends an empty `Vec<NewEvent>` with an `AppendCondition`. The condition check passes (no events to conflict), no events are written, but the returned `GlobalSequenceId` reflects the current sequence — not a new sequence. If the caller uses this as an `after` in a future `AppendCondition`, it may be wrong.

**Why it happens:** The existing code already returns early on empty events, but the semantics change under the new model — the caller's `AppendCondition` is never checked for empty appends.

**How to avoid:** For empty event lists, either (a) return an error ("nothing to append"), or (b) still run the condition check but return the current sequence. Decision: return the current sequence unchanged (existing behavior preserved), and document that an empty append is a no-op that does not validate the condition.

**Warning signs:** Tests that append empty vecs with an AppendCondition and assert on conflict behavior.

### Pitfall 2: Query::all() in AppendCondition

**What goes wrong:** Using `Query::all()` in an `AppendCondition` causes the condition to fail if ANY event has been appended after `after` — regardless of type or tags. This is extremely conservative and will conflict with all concurrent writers.

**Why it happens:** Developers expect `AppendCondition` to guard "their" data, not "all" data. `Query::all()` is right for `query()` reads but wrong for most `AppendCondition` use cases.

**How to avoid:** Document clearly that `AppendCondition.query` should scope to the tags/types the handler actually cares about. A handler managing `course:c1` should use `Query::match_tags([Tag::new("course:c1")])`.

**Warning signs:** Integration tests that always conflict after the first event.

### Pitfall 3: Tag Equality for HashSet Operations

**What goes wrong:** `Tag("course:c1")` and `Tag("course:C1")` are different tags (case-sensitive). Filtering with one won't match the other. Users who inconsistently case their tags will get empty results from queries that should match.

**Why it happens:** `HashSet<Tag>` uses Rust's default Hash/Eq which is case-sensitive. The library is "unopinionated about tag conventions" — it cannot normalize case.

**How to avoid:** Document that tag comparison is case-sensitive and exact. The library cannot enforce conventions, but can warn in documentation.

**Warning signs:** Queries that return zero events when events are expected — check tag casing first.

### Pitfall 4: Holding WriteLock Across Complex Operations

**What goes wrong:** The `InMemoryLogStore::append` acquires the write lock, runs the conflict check, and then builds stored events — all under one lock acquisition. If event construction were to `await` anything, the lock would be held across the await point, which panics with `tokio::sync::RwLock` in a non-Send context.

**Why it happens:** The stored event construction loop includes `SystemTime::now()` which is synchronous. But if a future refactor introduces async work inside the lock, it will deadlock or panic.

**How to avoid:** Keep all work inside the write lock synchronous. Build stored events before the lock acquisition if possible, or confirm no async calls exist within the locked section.

**Warning signs:** `clippy::await_holding_lock` lint firing.

### Pitfall 5: Breaking the EventStream Associated Type

**What goes wrong:** The `LogStore` associated type `EventStream` is the concrete type returned by `query()`. After the revision, `EventLog::query()` must return `S::EventStream` to avoid re-boxing. `EventStreamExt` is a blanket impl — it cannot be the `EventStream` type itself.

**Why it happens:** Confusion between the stream type (what the store returns) and the extension trait (methods added to any stream).

**How to avoid:** `EventStreamExt` is implemented for all streams matching the item type — callers get its methods via `use event_sourcing::EventStreamExt`. The return type of `EventLog::query()` remains `Result<S::EventStream, StoreError>`.

### Pitfall 6: Re-exporting Tag without Serde Feature Gating

**What goes wrong:** Adding `#[derive(Serialize, Deserialize)]` to `Tag` makes `serde` a required dependency of the core crate for downstream users, even if they don't need serialization.

**Why it happens:** Serde derives on public types in a library crate propagate the dependency unconditionally.

**How to avoid:** `serde` is already a workspace dependency and a required dep in `event-sourcing/Cargo.toml` (needed for `serde_json::Value` in payload). So deriving Serialize/Deserialize on `Tag` adds zero new requirements.

## Open Questions

1. **Query empty-criteria meaning**
   - What we know: DCB spec uses criteria sets. An event store with no criteria could mean "match all" or "match nothing."
   - What's unclear: The bwaidelich reference implementation's exact behavior for `Query` with zero criteria. CONTEXT.md D-15 gives Claude's discretion.
   - Recommendation: Treat empty criteria as "match nothing." Provide `Query::all()` as the explicit opt-in for match-all behavior. This is safer — accidental empty queries fail visibly rather than silently scanning everything.

2. **`EventStreamExt` and `Unpin` requirement**
   - What we know: `futures::StreamExt::next()` requires the stream to be `Unpin` (or used with `pin_mut!`).
   - What's unclear: Whether requiring `Unpin` on the blanket impl is acceptable for all stream types returned by `LogStore::query`.
   - Recommendation: Add `Unpin` bound to the `EventStreamExt` blanket impl. `InMemoryEventStream` (`stream::Iter`) is `Unpin`. SQLite store (Phase 8) will need to ensure its stream type is `Unpin` or use `Box::pin`. Document this as a constraint.

3. **`futures` dependency in core crate**
   - What we know: `futures` is currently only in `event-sourcing-logstore-inmemory` (via workspace dep). `EventStreamExt::single()` and `::first()` need `StreamExt::next()`.
   - What's unclear: Whether to add `futures` to `event-sourcing/Cargo.toml` or use `futures_core` only and write `.next()` manually.
   - Recommendation: Add `futures` to `event-sourcing/Cargo.toml` as a dependency (it is already a workspace dependency). `StreamExt::next()` is the standard way to advance a `Stream` — implementing it manually with `Pin` and `poll_next` would be needless complexity.
