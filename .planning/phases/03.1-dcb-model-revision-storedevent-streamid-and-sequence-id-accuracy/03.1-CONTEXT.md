# Phase 03.1: DCB Model Revision — StoredEvent, StreamId, and Sequence ID Accuracy - Context

**Gathered:** 2026-04-07
**Status:** Ready for planning

<domain>
## Phase Boundary

Revise the core types (`StoredEvent`, sequence IDs, concurrency model) and the `LogStore` trait to align with the Dynamic Consistency Boundary (DCB) pattern. This replaces the traditional single-stream-per-event model with a tag-based event log where events carry zero or more tags, streams are virtual (defined by queries at read time), and optimistic concurrency is enforced via query-based conditions against the global sequence position.

This phase touches every layer: core types, `LogStore` trait, `InMemoryLogStore`, and `EventLog`. It must be complete before Phase 4 (Projection Engine) builds on top of these types.

</domain>

<decisions>
## Implementation Decisions

### StoredEvent Revision

- **D-01:** `StoredEvent.stream_id: StreamId` is removed. Replaced with `tags: HashSet<Tag>` — an event carries zero or more tags.
- **D-02:** `StoredEvent.stream_sequence: StreamSequenceId` is removed entirely. Events are identified and ordered solely by their global sequence position.
- **D-03:** Revised `StoredEvent` structure:
  ```rust
  pub struct StoredEvent {
      pub global_sequence: GlobalSequenceId,
      pub event_type: String,
      pub payload: serde_json::Value,
      pub tags: HashSet<Tag>,
      pub timestamp: SystemTime,
  }
  ```

### Tag Type

- **D-04:** `Tag` is a newtype over `String` — opaque, non-empty, validated. The library does not interpret tag contents or enforce any key:value convention.
- **D-05:** Users choose their own tag conventions (e.g., `"course:c1"`, `"premium"`, `"region:eu"`). The library treats all tags as opaque strings.
- **D-06:** `HashSet<Tag>` is used for tags on `StoredEvent` and in queries — tags are unordered and unique per event.

### Sequence ID Model

- **D-07:** `StreamSequenceId` is removed from the library entirely. There is no per-stream sequencing in the DCB model.
- **D-08:** `GlobalSequenceId` remains as the sole ordering and identity mechanism. Monotonically increasing, starts at 1, `ZERO` = no events. No rename — the existing name is clear.
- **D-09:** `StreamId` type is removed. Its role is fully replaced by `Tag`.

### AppendCondition Revision

- **D-10:** `AppendCondition` is redesigned from version-based to query-based:
  ```rust
  pub struct AppendCondition {
      pub query: Query,
      pub after: GlobalSequenceId,
  }
  ```
  Semantics: "fail if any events matching `query` have been appended after position `after`."
- **D-11:** `AppendCondition` replaces the old `AppendCondition::Any` / `AppendCondition::ExpectedVersion(StreamSequenceId)` enum. The old enum is removed.
- **D-12:** An append with no condition (unconditional append) is expressed by passing `None` — `EventLog::append` takes `Option<AppendCondition>`.

### Query Type

- **D-13:** `Query` is a structured type for filtering events by tags and/or event types. It replaces the concept of reading by stream ID.
- **D-14:** Query API is explicit — no magic string parsing or prefix matching. Users construct queries with clear filter operations:
  - Filter by exact tag match
  - Filter by event type(s)
  - Combine filters (AND/OR semantics)
- **D-15:** Claude's discretion on the exact `Query` struct design (builder pattern, enum variants, or composable filter types). The key constraint: it must support tag matching and event type filtering, and be usable both for reads and for `AppendCondition`.

### LogStore Trait Revision

- **D-16:** `LogStore::append` signature changes: drops `stream_id` parameter. New signature:
  ```rust
  async fn append(
      &self,
      events: Vec<NewEvent>,
      condition: Option<AppendCondition>,
  ) -> Result<GlobalSequenceId, AppendError>;
  ```
- **D-17:** `LogStore::read_stream` is removed. Replaced with a query-based read:
  ```rust
  async fn read(&self, query: Query, from: GlobalSequenceId) -> Self::EventStream;
  ```
- **D-18:** `LogStore::read_all` stays but simplified — reads from a global position with no stream filter. May be expressible as `read(Query::all(), from)`.
- **D-19:** `LogStore::current_sequence` stays — returns the current highest `GlobalSequenceId` in the store.
- **D-20:** `LogStore::current_stream_sequence` is removed (no per-stream sequencing).

### NewEvent Revision

- **D-21:** `NewEvent` gains a `tags` field:
  ```rust
  pub struct NewEvent {
      pub event_type: String,
      pub payload: serde_json::Value,
      pub tags: HashSet<Tag>,
  }
  ```

### AppendError Revision

- **D-22:** `AppendError::ConcurrencyConflict` is revised — no longer carries `stream_id`, `expected`, `actual` stream sequence fields. The conflict means "events matching the query were found after the specified position."
- **D-23:** Claude's discretion on what metadata `ConcurrencyConflict` carries (e.g., the conflicting event's position, the query that matched).

### EventLog Revision

- **D-24:** `EventLog<S>` API mirrors the revised `LogStore` — `append`, `read`, `read_all` with the new signatures.
- **D-25:** `EventLogError::ConcurrencyConflict` revised to match the new `AppendError` shape.

### InMemoryLogStore Revision

- **D-26:** `InMemoryLogStore` updated to implement the revised `LogStore` trait. Tag-based filtering on reads, query-based concurrency checks on appends.
- **D-27:** All existing tests rewritten to use the tag-based model. Per-stream sequence tests removed.

### Claude's Discretion

- Module layout for `Tag`, `Query`, and revised types
- `Query` internal representation (struct, enum, builder — whatever is ergonomic)
- What metadata `ConcurrencyConflict` carries
- Whether `Tag` has a length limit or character validation beyond non-empty
- Test structure and coverage scope
- Whether `read_all` is a separate method or sugar for `read(Query::all(), from)`

</decisions>

<specifics>
## Specific Ideas

- The DCB reference implementation (bwaidelich/dcb-eventstore) should be studied by the researcher for exact `AppendCondition` check semantics and `Query` composition patterns.
- Tags use `HashSet` — unordered and unique per event. This was an explicit user preference over `Vec`.
- The library is unopinionated about tag conventions — no enforced `key:value` format. Users can use `"course:c1"`, `"premium"`, or any string.
- The multi-entity constraint problem (e.g., "student can't subscribe to more than 10 courses" AND "course can't exceed capacity") is the motivating use case for DCB tags — a single event tagged with both `student:s1` and `course:c1` is visible to both consistency boundaries.

</specifics>
