<decisions>
## Design Decisions

### Phase Scoping

- **D-01:** List fields require join machinery. A list field without joins is of limited value and would force a two-step implementation (primary-stream-only first, then extend for joins). Lists are implemented in Phase 5.1, after Phase 5 delivers join support.
- **D-02:** Phase 5 goal is expanded: join machinery + nested object joins + root-level joins. Not limited to nested objects — joins work at any level (root, nested object, list item).
- **D-03:** ESQL macro refactor (was Phase 5.1) is deferred to Phase 5.2, after list fields land. Phase number assignments:
  - Phase 5: Multi-stream joins + nested objects + catch-up
  - Phase 5.1: List fields
  - Phase 5.2: ESQL macro refactor

### List Key Model

- **D-04:** The list key is **implicit** — it is the tag value that matches the join's pattern. No explicit key declaration in the DSL. The `[]` notation signals "this is a list (multiple items)"; the `join` block inside determines both what a list item is and what its key is.
- **D-05:** DSL syntax: `orders[]: { join tag.starts_with("order:") as o ... }`. The `[]` is empty — key comes from the join.
- **D-06:** Tag-based key extraction expressions inside `[]` (e.g., `orders[tag.starts_with("order:")]`) are an implementation detail and are NOT exposed in the DSL. The join definition is the source of truth.
- **D-07:** Payload-field-based keys (e.g., `orders[c.OrderPlaced.order_id]`) are deferred to a later phase. Phase 5.1 implements tag-based keys only.

### Join Resolution

- **D-08:** Join resolution is **tag-based and implicit**. When a primary-stream event carries a tag matching the join's pattern, the engine uses that tag to identify the joined-stream instance. Example: `AccountantAssigned` on `customer:1` tagged `user:42` → engine joins the `user:42` stream for the `accountant` object.
- **D-09:** The same mechanism applies at all levels — root joins, nested object joins, and list item joins all use tag-matching on parent-stream events to resolve which stream instance to read.
- **D-10:** Primary-stream events are accessible inside nested object and list item blocks, provided they carry the appropriate tag. An `OrderPlaced` event tagged `{customer:1, order:42}` is visible from both the `customer:1` query and the `order:42` query. Within a list item scoped to `order:42`, handlers can reference `c.OrderPlaced` (primary stream) because that event carries the `order:42` tag. Processing is in global sequence order.

### Multiple Tags with Same Prefix

- **D-11:** **Nested objects:** A trigger event must carry exactly one tag matching the join pattern. Zero matching tags → the joined data does not update (no error). Multiple matching tags → **runtime error** with a clear, descriptive message. Silently picking the first match is fragile and rejected.
- **D-12:** **List items:** Multiple matching tags on a single event is fine — the event is applied to each matching list item. This enables batch operations (e.g., an event tagged `order:1` and `order:2` updates both items).

### Removal Semantics

- **D-13:** List items are removed via `removed_by event_ref` on the list block. The engine identifies which item to remove via the tag on the removal event — same implicit tag-based resolution as upsert.
- **D-14:** `removed_by` on a nested object: same keyword as list items (replacing `cleared_by` — see todo below). When the specified event fires, the object is set to null.
- **D-15:** `removed_by` on the root projection (tombstone — marking the whole instance as deleted) is deferred to Phase 7 (ProjectionObserver). The observer handles downstream cleanup when an instance is tombstoned.

### DSL Consistency

- **D-16:** `cleared_by` on object fields is renamed to `removed_by` for consistency with list item removal. This is a breaking change to the DSL and JSON schema. Tracked in `.planning/todos/pending/rename-cleared_by-to-removed_by.md`. Should be applied during Phase 5 before lists land, to avoid migrating tests twice.

### Multi-Instance Isolation (Test Requirement)

- **D-17:** Events tagged `customer:1` and `customer:2` must produce two separate read model instances — never merged. This is a mandatory test for Phase 5 / Phase 5.1. The `query` filter scopes events per instance; the test verifies the engine respects that boundary.

### Deferred to Separate Discussion

- **D-18:** The **JSON representation of joins** in `ProjectionDefinition` — how `join` blocks serialize, how nested join scoping works, how the engine resolves tag-based joins from the JSON definition — is a dedicated discussion topic. **Do not plan Phase 5 without this discussion.** Start Phase 5 `discuss-phase` with JSON join representation as the first agenda item.

### Claude's Discretion

- Internal representation of list state in the engine fold (e.g., `IndexMap<String, serde_json::Value>` keyed by tag value)
- How tag matching is implemented in the engine during fold (likely reuses `TagFilter` evaluation from Phase 03.2)

</decisions>

- `event-sourcing-macros/src/projection_macro.rs` — `parse_field_decl` is the extension point. Phase 5 adds `join` keyword parsing; Phase 5.1 adds `field[]:` list syntax.

### Established Patterns
- Scalar and object field specs use `IndexMap<EventType, HandlerSpec>` for handler registration — list item sub-fields follow the same pattern.
- `#[serde(untagged)]` on `FieldSpec` discriminates Object from Scalar via `"type"` key — a new `List` variant needs its own discriminator (`"type": "list"`).
- `cleared_by: Vec<EventType>` on `ObjectFieldSpec` — the `removed_by` rename preserves this structure but changes the field name.

### Integration Points
- Phase 5 adds a `join` parsing path to `parse_field_decl` and a new `JoinSpec` type in `definition.rs`.
- Phase 5.1 adds `ListFieldSpec` to `definition.rs` and extends the engine fold to accumulate `IndexMap<String, serde_json::Value>` for list state.
- Phase 5 and 5.1 both require the `removed_by` rename (D-16) to be applied first.

<specifics>
## Specific Ideas

- The `[]` in list field syntax (`orders[]: { ... }`) is intentionally empty — the key is implicit from the `join` inside. This keeps the DSL clean and avoids exposing tag extraction as a user-facing concept.
- For the multi-instance isolation test (D-17): create a projection over `tag.starts_with("customer:")`, append events tagged `customer:1` and `customer:2`, run the projection for each instance separately, and assert they produce independent read model values.
- The `join` keyword is syntactically new in Phase 5. It can appear at root level (inside the outer `projection! { }` block) or inside a nested object block or list item block. At root level it joins another stream's events into the top-level fields. Inside a nested object it scopes the join to that object's sub-fields.

</specifics>

<deferred>
## Deferred Ideas

### JSON join representation (Phase 5 discuss-phase — mandatory)
How `join` blocks serialize in `ProjectionDefinition` JSON, how the engine resolves tag-based joins from the definition, and how nested join scoping works. This must be resolved before Phase 5 can be planned. Start Phase 5 discuss-phase with this as the first agenda item.

### Payload-field-based list keys
`orders[c.OrderPlaced.order_id]` — using an event payload field as the list key instead of a tag. Deferred after Phase 5.1 (tag-based keys only in v1 list implementation).

### Payload-field-based removal
`removed_by c.OrderCancelled.order_id` — specifying the removal key from an event payload field. Deferred after Phase 5.1 (tag-based removal only).

### Root-level `removed_by` (tombstone)
`} removed_by c.CustomerDeactivated` at the outer projection level. Tombstone semantics where the ProjectionObserver handles downstream cleanup. Deferred to Phase 7 (Observer Infrastructure).

### Primary-stream-only list fields (no join)
List items populated entirely from the primary stream, keyed by a tag on the primary-stream events. Low value without join support; may be a natural fallout of Phase 5.1 implementation.

</deferred>
