### Tag matching — `event-sourcing/src/query.rs:60-78`
```rust
pub fn event_matches_criterion(event: &StoredEvent, criterion: &Criterion) -> bool {
    let type_match =
        criterion.event_types.is_empty() || criterion.event_types.contains(&event.event_type);
    let tag_match =
        criterion.tags.is_empty() || criterion.tags.iter().all(|t| event.tags.contains(t));
    type_match && tag_match

pub fn event_matches_query(event: &StoredEvent, query: &Query) -> bool {
    if query.criteria.is_empty() {

}
```

## 4. Serde Format Decision

### Current state
- `Criterion` has **NO serde derives**
- `Query` has **NO serde derives**
- `AppendCondition` has **NO serde derives**
- `Tag` HAS serde derives (already serializable)
- `HashSet<String>` serializes as JSON array natively

### Required additions
Add `serde::Serialize, serde::Deserialize` to all four types. Default serde format for externally-tagged enums:

```rust
#[derive(Serialize, Deserialize)]
pub enum TagFilter {
    Equals(Tag),
    StartsWith(String),
    EndsWith(String),
    And(Vec<TagFilter>),
    Or(Vec<TagFilter>),
}
```

Produces (default externally-tagged):
```json
{ "Equals": "order:o1" }
{ "StartsWith": "order:" }
{ "And": [ { "Equals": "order:o1" }, { "StartsWith": "premium:" } ] }
{ "Or": [ { "Equals": "a" }, { "Equals": "b" } ] }
```

**Recommendation:** Use the default externally-tagged format. It is stable, well-known, recursive-safe (standard serde behaviour for `Vec<T>` where `T: Serialize`), and requires zero attribute configuration.

**Alternative considered (not recommended):** `#[serde(tag = "type")]` internally-tagged enum — rejected because serde does not support internally-tagged enums with newtype variants containing non-struct types, and `Equals(Tag)` is exactly that. Default format has no such restriction.

## 5. Evaluation Function Placement

**Recommendation:** Method on `TagFilter`:
```rust
impl TagFilter {
    pub fn matches(&self, tags: &HashSet<Tag>) -> bool { ... }
}
```

**Rationale:**
- The existing pattern in this codebase places `event_matches_criterion`/`event_matches_query` as free functions in `query.rs` because they operate on TWO top-level types (`StoredEvent` + `Criterion`/`Query`). Keeping that pattern for existing functions is consistent.
- But `TagFilter::matches(&self, tags: &HashSet<Tag>)` is a recursive algorithm that reads from `self` — idiomatic Rust puts this on the type. It enables ergonomic call-chaining and keeps discoverability (`tag_filter.matches(&event.tags)`).
- `event_matches_criterion` will delegate to `tag_filter.matches(&event.tags)` — the free function stays where it is, only its inner logic changes. Best of both worlds.

## 6. Edge Cases

| Case | Semantic | Rationale |
|------|----------|-----------|
| `TagFilter::And(vec![])` | returns `true` (vacuous truth) | Standard fold-with-true; mirrors `Iterator::all` on empty iterator; mathematically standard |
| `TagFilter::Or(vec![])` | returns `false` (vacuous false) | Standard fold-with-false; mirrors `Iterator::any` on empty iterator |
| `TagFilter::Equals(t)` against empty event tags | returns `false` | `HashSet::contains(&t)` is `false` on empty set |
| `TagFilter::StartsWith("")` | returns `true` if event has ≥1 tag (every string starts with `""`) | Fine but callers should avoid; could add a debug_assert or simply document |
| `TagFilter::EndsWith("")` | returns `true` if event has ≥1 tag | Same as above |
| Nested depth | No structural limit; practical depth bounded by projection authors | serde handles arbitrary nesting via recursion; stack overflow risk only at pathological depths (10,000+). Not a concern. |
| `Criterion.tag_filter = None` | matches ANY tag set (including empty) — per D-04 | Preserves previous `tags: HashSet::new()` behaviour |
| `Query.criteria = vec![]` | matches nothing — unchanged from current behaviour (query.rs:71-73) | Same |

**Recommendation:** Add explicit unit tests for `And(vec![])` → true and `Or(vec![])` → false so the choice is pinned down and discoverable.

## 8. Risk Flags

1. **Serde derives are a new cross-cutting change.** `Criterion`, `Query`, and `AppendCondition` have never been serde-serializable. Adding these derives requires all their fields to be serde-serializable. `HashSet<String>` and `HashSet<Tag>` already are; `GlobalSequenceId` (inside `AppendCondition`) is **not** (checked types.rs:35-37 — no serde derives on `GlobalSequenceId`). **The planner MUST either (a) add serde derives to `GlobalSequenceId` or (b) scope AppendCondition serde to Phase 04.** Recommendation: add derives to `GlobalSequenceId` in this phase — trivial (`#[derive(Serialize, Deserialize)]` on a newtype around `u64`) and completes the serializable surface that Phase 04 needs.

2. **Public API migration** — `Criterion.tags` is a public field. Any downstream consumer (there are none yet, but this is a library) constructing `Criterion { ... }` directly breaks. Acceptable because the library is pre-1.0 and Phase 03.1 already shipped a breaking revision; note in phase summary.

3. **`tag_filter: Option<TagFilter>` vs no-option** — D-04 makes `None` explicit for "match any". The alternative (`TagFilter::MatchAny` variant) was not chosen. The planner should NOT re-litigate this — implement exactly what D-04 says.
