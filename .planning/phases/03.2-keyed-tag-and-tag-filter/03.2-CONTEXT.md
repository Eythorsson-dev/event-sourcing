# Phase 03.2: KeyedTag and TagFilter — Expressive Tag Scoping - Context

**Gathered:** 2026-04-09
**Status:** Ready for planning

<domain>
## Phase Boundary

Extend the core `Criterion` type to replace exact-match `HashSet<Tag>` with an expressive `TagFilter` enum, and introduce a `KeyedTag` type that formalizes the `key:value` tag convention. This is a targeted revision of Phase 03.1's type system — no new storage behaviour, no new trait methods. All existing tests must continue to pass.

**Scope:** Core crate (`event-sourcing`) and `InMemoryLogStore` (`event-sourcing-logstore-inmemory`) only. No other crates change.

**Depends on:** Phase 03.1 (tag-based model, `Query`, `Criterion`, `AppendCondition`)

</domain>

<decisions>
## Implementation Decisions

### Why This Phase Exists

- **D-01:** `ProjectionDefinition` needs to declare which stored events belong to which projection instance (for observer routing in Phase 7). Event type alone is insufficient — `OrderPlaced` events for `order:o1` and `order:o2` must be distinguishable. Tag-based scoping via filter operators (`starts_with`, `equals`) is the mechanism.
- **D-02:** `ProjectionDefinition.query` and `AppendCondition.query` must be the same `Query` type. In the DCB model the consistency boundary IS the projection query — using different types breaks that alignment. Therefore `TagFilter` must be part of the core `Query`/`Criterion` type, not a separate projection-only type.

### KeyedTag

- **D-03:** `KeyedTag` is a newtype with `key: String` and `value: String`. It implements `Into<Tag>`, producing `Tag::new(format!("{}:{}", key, value))`. This formalizes the implicit `key:value` convention used throughout the tag model.
- **D-04:** `KeyedTag::new(key, value)` is the constructor. Both `key` and `value` must be non-empty (same invariant as `Tag`). Returns `Result<KeyedTag, InvalidTag>`.
- **D-05:** `KeyedTag` is exported from the core crate root alongside `Tag`.

### TagFilter

- **D-06:** `TagFilter` is an enum with variants:
  ```rust
  pub enum TagFilter {
      Equals(Tag),
      StartsWith(String),
      EndsWith(String),
      And(Vec<TagFilter>),
      Or(Vec<TagFilter>),
  }
  ```
- **D-07:** `TagFilter` replaces `tags: HashSet<Tag>` in `Criterion`. The new field is `tag_filter: Option<TagFilter>`. `None` means "no tag filter — match any tags" (preserves the current behaviour of an empty `HashSet`).
- **D-08:** Builder/constructor methods on `Criterion` accept `impl Into<Tag>` for the `Equals` case — `KeyedTag` and `Tag` both work without explicit conversion at call sites.
- **D-09:** `TagFilter` derives `serde::Serialize` and `serde::Deserialize`. JSON representation uses tagged enums (serde default for enums with data).
- **D-10:** Evaluation semantics:
  - `Equals(tag)` — event must carry this exact tag
  - `StartsWith(prefix)` — event must carry at least one tag whose string value starts with `prefix`
  - `EndsWith(suffix)` — event must carry at least one tag whose string value ends with `suffix`
  - `And(filters)` — event must satisfy ALL filters in the vec
  - `Or(filters)` — event must satisfy ANY filter in the vec

### Criterion Changes

- **D-11:** `Criterion` before: `{ event_types: HashSet<String>, tags: HashSet<Tag> }`. After: `{ event_types: HashSet<String>, tag_filter: Option<TagFilter> }`.
- **D-12:** The existing `Query::match_tags(tags)` constructor is updated to produce `TagFilter::And(tags.map(TagFilter::Equals).collect())` — semantics unchanged, exact AND-of-equals matching preserved.
- **D-13:** Existing call sites that pass a `HashSet<Tag>` to `Criterion` are updated to use `TagFilter::Equals` or `TagFilter::And` as appropriate. Phase 03.1 tests must pass without semantic change.

### InMemoryLogStore

- **D-14:** `InMemoryLogStore` must evaluate `TagFilter` during `query()` and `append()` condition checks. The evaluation function is pure (`fn matches_tag_filter(tags: &HashSet<Tag>, filter: &TagFilter) -> bool`) and lives in the core crate alongside `TagFilter`.
- **D-15:** `starts_with` and `ends_with` operate on `tag.as_str()` — they match the full tag string (e.g., `starts_with("order:")` matches `"order:o1"`).

### Usage Pattern (for downstream phases)

- **D-16:** `ProjectionDefinition.query` (Phase 4) uses `starts_with` for collection-level scope — one definition covers all instances of a collection type:
  ```rust
  // Definition (general — covers all orders):
  query: Query::tag_starts_with("order:")

  // Runtime (per-instance fetch + consistency):
  let instance_query = Query::tag_equals(Tag::new("order:o1")?);
  ```
- **D-17:** Observer routing (Phase 7): when an event arrives with tag `order:o1`, the observer checks each registered projection's `definition.query` against the event. `starts_with("order:")` matches → update the OrderView instance for `o1`. Instance ID is extracted as the suffix after `order:`.

### Claude's Discretion

- Whether `TagFilter` evaluation lives in a free function in the core crate or as a method on `TagFilter`
- Whether `Query` gets convenience constructors `Query::tag_starts_with`, `Query::tag_ends_with` or the caller builds via `TagFilter` directly
- Test coverage scope and structure

</decisions>

<specifics>
## Specific Ideas

- `KeyedTag::new("order", "o1")` produces `Tag("order:o1")` via `Into<Tag>`. The caller decides the separator convention — the library uses `:` by convention but does not enforce it (tags remain opaque strings; `KeyedTag` is a convenience constructor, not a parsing primitive).
- `TagFilter::StartsWith("order:")` — note the colon is included in the prefix string so it matches `order:o1` but not `ordering:anything`. Callers are responsible for including the separator in the prefix/suffix strings.
- For the `And([Equals(t1), Equals(t2)])` case (equivalent to old `HashSet<Tag>` with two tags), the existing `Query::match_tags` helper should be updated to produce this naturally so call sites don't need to change.

</specifics>

<deferred>
## Deferred Ideas

- Tag parsing helpers (extract key/value from an existing `Tag` string) — useful for observer routing in Phase 7 but not needed here. The library does not interpret tag contents; that's Phase 7's concern.
- `TagFilter::Not(Box<TagFilter>)` — negation filter. Not needed for v1 use cases; defer.
- Regex or glob tag filters — out of scope; `starts_with` / `ends_with` cover the realistic cases.

</deferred>
