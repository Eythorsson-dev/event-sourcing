# Phase 03.2: TagFilter — Expressive Tag Scoping - Context

**Gathered:** 2026-04-09
**Status:** Ready for planning

<domain>
## Phase Boundary

Extend the core `Criterion` type to replace exact-match `HashSet<Tag>` with an expressive `TagFilter` enum. This is a targeted revision of Phase 03.1's type system — no new storage behaviour, no new trait methods, no new public types beyond `TagFilter`. All existing tests must continue to pass.

**Scope:** Core crate (`event-sourcing`) and `InMemoryLogStore` (`event-sourcing-logstore-inmemory`) only. No other crates change.

**Depends on:** Phase 03.1 (tag-based model, `Query`, `Criterion`, `AppendCondition`)

</domain>

<decisions>
## Implementation Decisions

### Why This Phase Exists

- **D-01:** `ProjectionDefinition` needs to declare which stored events belong to which projection instance (for observer routing in Phase 7). Event type alone is insufficient — `OrderPlaced` events for `order:o1` and `order:o2` must be distinguishable. Tag-based filter operators (`starts_with`, `equals`) are the mechanism.
- **D-02:** `ProjectionDefinition.query` and `AppendCondition.query` must be the same `Query` type. In the DCB model the consistency boundary IS the projection query — using different types breaks that alignment. Therefore `TagFilter` must live in the core `Query`/`Criterion` type, not a separate projection-only type.

### TagFilter

- **D-03:** `TagFilter` is an enum with variants:
  ```rust
  pub enum TagFilter {
      Equals(Tag),
      StartsWith(String),
      EndsWith(String),
      And(Vec<TagFilter>),
      Or(Vec<TagFilter>),
  }
  ```
- **D-04:** `TagFilter` replaces `tags: HashSet<Tag>` in `Criterion`. The new field is `tag_filter: Option<TagFilter>`. `None` means "no tag filter — match any tags" (preserves the current behaviour of an empty `HashSet`).
- **D-05:** `TagFilter` derives `serde::Serialize` and `serde::Deserialize`. JSON representation uses serde's default tagged enum format.
- **D-06:** Evaluation semantics:
  - `Equals(tag)` — event must carry this exact tag
  - `StartsWith(prefix)` — event must carry at least one tag whose string value starts with `prefix`
  - `EndsWith(suffix)` — event must carry at least one tag whose string value ends with `suffix`
  - `And(filters)` — event must satisfy ALL filters in the vec
  - `Or(filters)` — event must satisfy ANY filter in the vec

### Criterion Changes

- **D-07:** `Criterion` before: `{ event_types: HashSet<String>, tags: HashSet<Tag> }`. After: `{ event_types: HashSet<String>, tag_filter: Option<TagFilter> }`.
- **D-08:** The existing `Query::match_tags(tags)` constructor is updated to produce `TagFilter::And(tags.map(TagFilter::Equals).collect())` — semantics unchanged, exact AND-of-equals matching preserved.
- **D-09:** Existing call sites that pass a `HashSet<Tag>` to `Criterion` are updated to use `TagFilter::Equals` or `TagFilter::And` as appropriate. Phase 03.1 tests must pass without semantic change.

### InMemoryLogStore

- **D-10:** `InMemoryLogStore` must evaluate `TagFilter` during `query()` and `append()` condition checks. The evaluation function is pure (`fn matches_tag_filter(tags: &HashSet<Tag>, filter: &TagFilter) -> bool`) and lives in the core crate alongside `TagFilter`.
- **D-11:** `StartsWith` and `EndsWith` operate on `tag.as_str()` — they match the full tag string (e.g., `StartsWith("order:")` matches `"order:o1"` but not `"ordering:foo"`). Callers are responsible for including the separator in prefix/suffix strings.

### Usage Pattern (for downstream phases)

- **D-12:** `ProjectionDefinition.query` (Phase 4) uses `StartsWith` for collection-level scope — one definition covers all instances of a collection type:
  ```rust
  // Definition (general — covers all orders):
  query: Query { criteria: vec![Criterion {
      event_types: HashSet::new(),
      tag_filter: Some(TagFilter::StartsWith("order:".into())),
  }]}

  // Runtime (per-instance fetch + consistency check):
  let instance_query = Query { criteria: vec![Criterion {
      event_types: HashSet::new(),
      tag_filter: Some(TagFilter::Equals(Tag::new("order:o1")?)),
  }]};
  ```
- **D-13:** Observer routing (Phase 7): when an event arrives with tag `order:o1`, the observer evaluates each registered projection's `definition.query` against the event. `StartsWith("order:")` matches → update the OrderView instance for `o1`. Instance ID extraction from the tag suffix is a Phase 7 concern.

### Claude's Discretion

- Whether `TagFilter` evaluation lives as a free function or a method on `TagFilter` itself
- Whether `Query` gets named convenience constructors (`Query::tag_starts_with`, etc.) or callers build `TagFilter` directly
- Test coverage scope and structure

</decisions>

<specifics>
## Specific Ideas

- `TagFilter::StartsWith("order:")` — the colon is part of the prefix string, so it matches `order:o1` but not `ordering:anything`. This is intentional — callers control the separator convention.
- For the `And([Equals(t1), Equals(t2)])` case (equivalent to old `HashSet<Tag>` AND semantics), the existing `Query::match_tags` helper should be updated to produce this form naturally so no call sites need manual changes.

</specifics>

<deferred>
## Deferred Ideas

### KeyedTag type + helper methods
A `KeyedTag` struct with `key: String` and `value: String` implementing `Into<Tag>`, plus convenience constructors on `TagFilter` like `TagFilter::key_equals("order", "o1")` that internally build the correct tag string. Useful for ergonomics once `TagFilter` is stable. Tracked in `.planning/todos/pending/keyed-tag-helper.md`.

### TagFilter::Not
Negation filter — not needed for v1 use cases; defer.

### Regex / glob tag filters
Out of scope; `StartsWith` / `EndsWith` cover realistic cases.

### Tag parsing helpers
Extract key/value from an existing `Tag` string — useful for observer routing in Phase 7 but not a library concern here.

</deferred>
