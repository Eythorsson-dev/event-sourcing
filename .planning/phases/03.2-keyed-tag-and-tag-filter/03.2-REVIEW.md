## Warnings

### WR-01: `Query::match_tags([])` silently matches all events

**File:** `event-sourcing/src/query.rs:67`
**Issue:** `Query::match_tags` wraps collected tags into `TagFilter::And(filters)`. When the caller passes an empty iterator, `filters` is empty and `TagFilter::And(vec![])` is vacuously true — matching every event. The public doc comment says "Match events carrying ALL of the specified tags" without noting this edge case. A caller who writes `Query::match_tags(user_supplied_tags)` where the collection can be empty will inadvertently create a match-all query instead of a match-nothing query.

**Fix:** Guard against the empty case explicitly, or update the contract in the doc comment to warn callers. The most defensive option:

```rust
/// Match events carrying ALL of the specified tags.
/// If `tags` is empty, returns `Query::all()` — vacuously true semantics from `And([])`.
/// Pass at least one tag to create a selective filter.
pub fn match_tags(tags: impl IntoIterator<Item = Tag>) -> Self {
    let filters: Vec<TagFilter> = tags.into_iter().map(TagFilter::Equals).collect();
    // And([]) is vacuously true — treat as match-all rather than silently surprising callers.
    if filters.is_empty() {
        return Query::all();
    }
    Query {
        criteria: vec![Criterion {
            event_types: HashSet::new(),
            tag_filter: Some(TagFilter::And(filters)),
        }],
    }
}
```

Alternatively, document the vacuous-true behaviour explicitly so callers are not surprised. Either path is acceptable; the current state is a silent footgun.

### WR-02: `GlobalSequenceId::next()` overflows on `u64::MAX`

**File:** `event-sourcing/src/types.rs:52`
**Issue:** `Self(self.0 + 1)` is an unchecked integer addition. On `u64::MAX` (18446744073709551615) this wraps in release mode, silently producing `GlobalSequenceId(0)` — aliasing `ZERO`. In a library crate this is a correctness hazard: consumers calling `next()` in sequence-generation logic would silently corrupt ordering. Debug builds panic via overflow check, but release builds do not.

**Fix:** Use `checked_add` or `saturating_add` with an explicit panic or `Option` return:

```rust
pub fn next(self) -> Self {
    Self(
        self.0
            .checked_add(1)
            .expect("GlobalSequenceId overflow: u64::MAX exceeded"),
    )
}
```

Using `checked_add` + `expect` ensures the failure is loud in both debug and release. If callers need to handle overflow gracefully, change the signature to `-> Option<Self>`.

### IN-01: Concurrency test comment overstates parallelism guarantee

**File:** `event-sourcing-logstore-inmemory/src/lib.rs:560`
**Issue:** The test `concurrent_condition_conflict` uses `tokio::join!` to "concurrently" submit two appends. The comment "Two concurrent appends with the same condition checking after ZERO" and the assertion that "exactly one should succeed and one should conflict" relies on the write lock serializing them — which it does. However, `tokio::join!` provides cooperative interleaving, not OS-level parallelism. The test is deterministic and passes correctly, but the comment implies a concurrency guarantee stronger than what `tokio::join!` on a single-threaded test executor provides. This may mislead future contributors.

**Fix:** Update the comment to clarify the test verifies serialization under the write lock:

```rust
// tokio::join! interleaves the two appends cooperatively.
// The write lock in `append` serializes them — exactly one will see
// the other's event and return ConcurrencyConflict.
```
